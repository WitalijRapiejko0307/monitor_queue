# Опрос очереди только при активных наблюдениях

Статус: согласовано и реализовано в планировщике.

## Правило

Планировщик читает API зоны ожидания и пишет очередь в БД только если есть хотя бы одна подписка в статусе `active` или `alerting`.

Число таких подписок не умножает опросы. Два и более активных запроса от разных пользователей (в том числе на разные пункты, направления и типы транспорта) обслуживаются одним общим срезом за тик.

## Цикл `run_fetch_and_evaluate`

1. Посчитать подписки со статусом `active` или `alerting`.
2. Если их ноль — выйти сразу:
   - нет HTTP-запроса к источнику;
   - нет новой строки в `queue_snapshots` и `queue_values`;
   - нет событий `snapshot_fetch_*` в `event_log`;
   - в stdout одна строка, что опрос пропущен: активных наблюдений нет.
3. Если их одна или больше — один вызов `fetch_and_store_snapshot`, затем `process_subscriptions_for_snapshot` по всем таким подпискам.

Запись снапшота внутри `fetch_and_store_snapshot` не меняется: успешный срез пишется только когда числа изменились; ошибка источника пишется, чтобы сбой был виден. Эти записи появляются только в тике, который дошёл до опроса, то есть когда наблюдение уже есть.

Каждая подписка по-прежнему читает нужную ячейку из этого одного снапшота. События `window_state`, `rule_check` и уведомления остаются привязанными к подписке и пишутся, когда факты изменились.

## Что не меняется

- Ручной снимок из админки по-прежнему один вызов `fetch_and_store_snapshot` и не зависит от числа подписок.
- Контракт `fetch_and_store_snapshot` не меняется: проверку «есть ли кого обслуживать» делает джоб до вызова.

## Критерии приёмки

1. При нуле подписок `active` и `alerting` за интервал нет запроса к border API и нет новых строк в `queue_snapshots` и `event_log`.
2. При одной и более таких подписках цикл опроса и уведомлений работает как сейчас.
3. При двух и более активных запросах от разных пользователей за один тик ровно один HTTP-опрос и не больше одного нового снапшота.
4. Админская команда ручного снимка работает и без активных подписок.

## Затронутый код

- `app/scheduler/jobs.py` — подсчёт активных подписок до `fetch_and_store_snapshot`.
- Запрос подсчёта рядом с обработкой подписок: `count` по `subscriptions.status in (active, alerting)`.
- `app/domain/snapshot_service.py` без смены контракта.

Первый снимок после появления первой подписки приходит на ближайшем тике планировщика (до интервала опроса).
